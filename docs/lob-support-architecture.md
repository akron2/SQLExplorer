# Поддержка LOB и экспорт в Excel: архитектура

Дата: 2026-09-12. Статус: реализовано и проверено 2026-09-13 (этапы 1 и 2). Задача: [DATA-001](../docs/backlog.md) и [DATA-003](../docs/backlog.md).
Связанные документы: [архитектура](architecture.md), [производительность](performance.md), [бэклог](backlog.md).

## Цель и критерии успеха

1. Пользователь видит LOB-значения (Oracle CLOB/NCLOB/BLOB/BFILE, PostgreSQL text/bytea) в отдельном просмотрщике: первые 8 KiB сразу, «Показать ещё» до 1 MiB, дальше только сохранение.
2. Полное значение сохраняется в файл потоково, без накопления в renderer: Oracle — потоком из локатора, PostgreSQL — из значения драйвера. Прогресс и отмена.
3. Бинарь просматривается как hex и как текст в выбранной кодировке.
4. Память renderer ограничена: в состоянии интерфейса не более 1 MiB на открытое значение.
5. Экспорт в Excel (.xlsx) добавляется рядом с CSV: LOB-режимы «маркеры», «частично» (только текст), «каждый LOB отдельным файлом с гиперссылкой»; полная выгрузка остатка курсора остаётся в DATA-002.
6. Все сценарии проверены на живых Oracle 21c XE и PostgreSQL 10.23 локального стенда.

## Ограничения и допущения

- node-oracledb 7.0.1: LOB-колонки приходят локаторами (`Lob`), `lob.length` доступен без чтения данных, `lob.getData(offset, amount)` читает фрагмент (offset — 1-based UCS-2 code points для CLOB, байты для BLOB), `lob.pipe()` — поток в файл. Локатор действителен, пока открыто соединение; ресурс освобождается `lob.destroy()`.
- PostgreSQL `pg`/`pg-cursor`: сервер присылает значение поля целиком, частичное ленивое чтение `bytea`/`text` невозможно. Значение живёт в памяти worker, поэтому вводится бюджет.
- Excel: максимум 32 767 символов в ячейке, 1 048 576 строк, 16 384 колонки; потоковый writer ExcelJS и относительные гиперссылки проверены спайком и живым тестом.
- Renderer не пишет на диск: файловые диалоги и запись — в main, поток LOB идёт worker → диск.

## Выбранное решение

### Компоненты

```
Renderer                  Main                     Worker (utility process)
┌───────────────┐ invoke  ┌───────────────┐  call   ┌───────────────────────────┐
│ ResultPanel   │────────▶│ runtime mgr   │────────▶│ cursor state per execId   │
│ LobViewer     │◀─chunk──│ маршрут по    │◀─chunk──│ LobStore: локаторы Oracle │
│ до 1 MiB      │         │ executionId   │         │ / значения PG (бюджет)    │
└───────┬───────┘         │ FileService   │         │ readLob/saveLob/          │
        │ saveLob         │ Save-диалог   │         │ cancelLobSave/confirm     │
        └────────────────▶└───────┬───────┘         └───────────────────────────┘
                                  │ stream to disk (main открывает путь, worker пишет)
```

### Контракт значений

`CellValue` расширяется вариантом:

```ts
interface LobCellValue {
  kind: 'lob';
  subtype: 'CLOB' | 'NCLOB' | 'BLOB' | 'BFILE' | 'TEXT' | 'BYTEA';
  size: number | null;
  sizeUnit: 'chars' | 'bytes';
  available: boolean;      // false, если PG-значение не удержано из-за бюджета
  note?: 'budget';
}
```

- Oracle LOB любого размера → локатор в `LobStore` + маркер в ячейке.
- PostgreSQL `bytea` любого размера → значение в `LobStore` + маркер (base64 в ячейках и CSV больше не используется).
- PostgreSQL `text`/`varchar` до 8 KiB — как раньше, строкой; больше — в `LobStore` + маркер.
- `NULL` остаётся `null`; пустой LOB — маркер с размером 0.

### Хранение и жизненный цикл

- `LobStore` привязан к `CursorState` и адресуется ключом `исполнение → «строка:колонка»`.
- Результат запроса с LOB больше не «забывается» при `hasMore = false`: маршрутизация `executionId → runtime` живёт до следующего Execute в этом документе, disconnect или падения runtime. Вытеснение — `closeSessionCursors` (новый Execute), commit/rollback, disconnect, закрытие приложения.
- Oracle `ResultSet` для результатов с LOB не закрывается до освобождения исполнения (страховка от инвалидирования локаторов); `lob.destroy()` — при освобождении.
- Budget PG: стартовые 256 MiB на worker. При переполнении worker приостанавливает сериализацию страницы, шлёт событие `lob-budget`; интерфейс показывает модал «загрузить ещё 256 МиБ?». «Да» — лимит растёт; «нет»/таймаут — ячейка получает `available: false`. Oracle бюджета не требует.
- Отмена сохранения: `lob.destroy()`, удаление недописанного файла.

### IPC

- `db:read-lob` → `LobChunkResult` (`offset`/`nextOffset` в единицах значения, `eof`, `utf8`/`base64`).
- `db:save-lob` — main показывает Save-диалог, worker пишет файл сам, возвращает путь и число байт; `db:lob-cancel-save`, событие `db:lob-progress`.
- `db:lob-budget` (worker → main → renderer) и `db:lob-budget-confirm` (ответ).

### Просмотрщик

- Открытие: двойной клик или правый клик → «Открыть значение»; в ячейке — компактный маркер.
- Текст: `<pre>` с выделением, «Показать ещё», «Копировать загруженное», «Сохранить в файл…».
- Бинарь: вкладки Hex и «Текст» (кодировки из списка приложения, декодирование накопленного буфера через iconv-lite).
- Кнопка «Показать ещё» прекращает работу на потолке 1 MiB, дальше только сохранение.

### Excel-экспорт (этап 2)

- Writer — ExcelJS streaming (`Excel.stream.xlsx.WorkbookWriter`) в main; проверка гиперссылок — spike до основной работы.
- Строки передаются renderer → main чанками с подтверждением; LOB-содержимое main тянет у worker (`readLob` / `saveLob` в каталог экспорта).
- Режимы LOB: маркеры; частично (текст до 32 000 символов, бинарь не выгружается); каждый LOB в файл с относительной гиперссылкой в подкаталоге `<имя>.lobs`.
- Диалог спрашивает, догрузить ли оставшиеся строки. CSV сохраняется отдельной кнопкой.
- Ограничения Excel обрабатываются явно: усечение текста, лимит строк/колонок, предупреждение о лимите гиперссылок.

## Ключевые решения и обоснование

| Решение | Альтернативы | Почему так |
|---|---|---|
| Worker — единственный держатель тяжёлых значений | Тянуть LOB при получении страницы; писать на диск сразу | Первое нарушает `performance.md:67` и DATA-002, второе пишет данные БД на диск без запроса |
| Union-маркер в `CellValue` | Маркер-строка с префиксом | Строковый маркер конфликтует с реальными данными и хрупок |
| Потоковое сохранение worker → диск | Накопить в renderer и сохранить | Renderer не должен держать больше 1 MiB |
| Держать Oracle ResultSet до освобождения | Закрывать при `hasMore = false` | Локаторы гарантированно живы; цена — один открытый курсор на исполнение |
| Бюджет PG с подтверждением | Жёсткий отказ; слив во временный файл; без лимита | Отказ теряет данные, слив неявно пишет БД на диск, без лимита — риск OOM |
| Excel: writer в main, строки чанками | Генерация в renderer | Renderer-память и повторное использование для DATA-002 |
| CSV остаётся | Заменить CSV на Excel | Совместимость и дешёвая альтернатива для простых выгрузок |

## Отклонённые альтернативы

- **Полное чтение LOB при fetch** (`fetchAsString`/`fetchAsBuffer`): несовместимо с большими значениями и бюджетом памяти.
- **Частичное чтение PostgreSQL через `substring()`**: требует переписать произвольный SQL, недопустимо.
- **Повторный запрос для просмотра**: база могла измениться; запрещено правилами экспорта в `performance.md`.
- **Писать LOB во временные файлы автоматически**: неявная запись данных БД на диск; оставлено как возможное развитие при реальных переполнениях.

## Риски и открытые вопросы

По итогам реализации:

- Локатор Oracle подтверждён живым тестом: чтение чанками и сохранение работают и после `hasMore = false`, при этом `ResultSet` удерживается до освобождения исполнения.
- `getData()` и `pipe()` на одном локаторе конфликтуют: `pipe()` не сбрасывает позицию и портит повторное сохранение. Сохранение переведено на позиционный цикл `getData(offset, amount)`.
- ExcelJS streaming + относительные гиперссылки проверены спайком на 50 000 ссылок; библиотека подключена внешней зависимостью main (`external`), чтобы не попасть на browser-сборку без `stream`.
- В renderer используется `TextDecoder` (+ собственная расшифровка UTF-32) вместо `iconv-lite`, потому что sandboxed renderer не имеет Node `buffer`.
- «Догрузить все строки» при экспорте временно использует накопление renderer — до DATA-002.
- Для очень массового режима файлов остаётся предупреждение о лимите гиперссылок Excel (~66 530 на лист).
