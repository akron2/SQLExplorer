# Автодополнение Oracle и PostgreSQL

Дата исследования: 2026-09-09. Статус: кандидаты и план оценки; движок не выбран окончательно.

Основной документ: [architecture.md](architecture.md). Производительность: [performance.md](performance.md).

## Решение на текущем этапе

Monaco предоставляет интерфейс подсказок, но поддержку семантики Oracle и PostgreSQL необходимо подключить отдельно. Полная разработка анализатора с нуля не является исходным планом.

Первым оценивается выделение двух модулей автодополнения Bytebase в один вспомогательный Go-процесс. При неудовлетворительном качестве одного диалекта его провайдер можно заменить независимо. Наличие исходников и тестов не подтверждает пригодность готовой интеграции: сборка, скорость и корректность кандидатных движков в SQLExplorer ещё не проверялись.

## Что требуется от подсказок

Базовый объём для обеих СУБД:

- Подходящие по позиции ключевые слова, схемы, таблицы, представления и колонки.
- Разрешение алиасов и контекста текущего выражения.
- CTE, вложенные запросы и разные области видимости одинаковых имён.
- Учёт соединения, доступных объектов, схемы, регистра и quoted identifiers.
- Работа с недописанным SQL, без блокировки редактора при ошибке разбора.
- Отсутствие переноса подсказок между разными базами и версиями текста.
- Ответы из кэша и ограниченное по времени фоновое обновление.

Полнота анализа тел PL/SQL и PL/pgSQL остаётся открытым вопросом. Подсказки локальных переменных, записей, курсоров, перегрузок и параметров процедур нужно оценивать отдельно от обычного SQL.

## Проверенные кандидаты

### Bytebase: Oracle и PostgreSQL

В исходниках есть отдельные реализации Completion для Oracle и PostgreSQL. Просмотрены код Oracle и его тестовые сценарии: в них представлены алиасы, CTE, вложенные источники, DML и несколько специфичных для Oracle конструкций. PostgreSQL использует отдельный модуль с контекстом схем и ссылок на таблицы.

Снимок Bytebase, использованный для ссылок: `b9d5ca0226db4aa865796cec716413a5654a16a0`.

- [Реализация Oracle](https://github.com/bytebase/bytebase/blob/b9d5ca0226db4aa865796cec716413a5654a16a0/backend/plugin/parser/plsql/completion.go).
- [Тесты Oracle](https://github.com/bytebase/bytebase/blob/b9d5ca0226db4aa865796cec716413a5654a16a0/backend/plugin/parser/plsql/completion_test.go).
- [Реализация PostgreSQL](https://github.com/bytebase/bytebase/blob/b9d5ca0226db4aa865796cec716413a5654a16a0/backend/plugin/parser/pg/completion.go).

Модули зависят от общих структур Bytebase, моделей метаданных и парсера Omni. Потребуется выяснить границу извлечения, размер зависимостей и стоимость поддержания адаптации. Это исходный код внутри продукта, а не заявленный автономный SDK с гарантированным API.

В просмотренном [README Omni](https://github.com/bytebase/omni/blob/c0a6ff1c3d894e5a87a1e4ed93384581a6aded83/README.md) Oracle-парсер обозначен как разрабатываемый, а completion — как планируемый, хотя в текущем дереве кода уже есть реализация. Несоответствие статуса и исходников требует проверки готовности; нельзя трактовать наличие файлов как обещание полной поддержки PL/SQL.

[Лицензия Bytebase](https://github.com/bytebase/bytebase/blob/b9d5ca0226db4aa865796cec716413a5654a16a0/LICENSE) отделяет обычный код под MIT от enterprise-частей и кода управления доступностью функций. При выделении модуля нужно определить точный набор используемых файлов и сохранить необходимые уведомления.

### Postgres Language Server

[Postgres Language Server](https://github.com/supabase-community/postgres-language-server) — отдельный готовый языковой сервер с LSP-интерфейсом. По документации он предлагает контекстные подсказки таблиц, колонок, функций, схем и сведения при наведении. Сведения о схеме кэшируются после подключения. [Описание автодополнения](https://pg-language-server.com/latest/features/editor_features/).

Это основная альтернатива для PostgreSQL, если она окажется качественнее или проще адаптации Bytebase. Цена — второй внешний компонент и отдельная интеграция его контекста соединения с SQLExplorer.

Ограничения следует учитывать при оценке:

- Поддержка PL/pgSQL в документации названа частичной.
- Подсказкам и сведениям об объектах нужен доступ к схеме БД.
- Проверка типов обращается к серверу через EXPLAIN.
- Расширенная диагностика через plpgsql_check может создавать функцию в транзакции для проверки её тела.

Для интеграции автодополнения автоматические операции проверки SQL на сервере и создание функций не включаются по умолчанию. Они должны быть отдельной возможностью, если она понадобится пользователю. Установка расширения в БД не относится к базовой настройке SQLExplorer. Источники: [PL/pgSQL](https://pg-language-server.com/latest/features/plpgsql/), [проверка типов](https://pg-language-server.com/latest/features/type_checking/).

### ANTLR, грамматика PL/SQL и antlr4-c3

В [antlr/grammars-v4](https://github.com/antlr/grammars-v4/tree/master/sql/plsql) есть грамматика PL/SQL. [antlr4-c3](https://github.com/mike-lischke/antlr4-c3) предоставляет движок поиска допустимых токенов и правил грамматики в позиции курсора. Текущий TypeScript-вариант c3 использует antlr4ng; генератор, runtime и версия c3 должны подбираться совместно.

Это резервный путь для Oracle при желании сохранить анализ на TypeScript. Потребуется собственная связь синтаксического контекста с таблицей символов, метаданными, алиасами и областями видимости. Готовая грамматика сама по себе не обеспечивает полное автодополнение объектов БД. Грамматику и её вспомогательные классы необходимо адаптировать и проверить на недописанном SQL.

Автор c3 отдельно отмечает стоимость обхода сложной грамматики. Ограничение анализируемого контекста и времени работы обязательно для нашего сценария отзывчивости. [Архитектура c3 и ограничение поиска](https://github.com/mike-lischke/antlr4-c3#constraining-the-search-space).

### Другие просмотренные решения

- [monaco-sql-languages](https://github.com/DTStack/monaco-sql-languages) не заявляет Oracle в перечне диалектов. Готовая интеграция с Monaco не решает задачу Oracle автоматически.
- [sqls](https://github.com/sqls-server/sqls) и [joe-re/sql-language-server](https://github.com/joe-re/sql-language-server) поддерживают PostgreSQL, но не заявляют Oracle. Они не выбраны общим движком для обеих СУБД.
- [plsql-language](https://github.com/zabel-xyz/plsql-language) содержит подсказки членов пакетов из файлов и расширение списков таблиц/полей. Это расширение VS Code, а не готовый автономный модуль нашего приложения.

## Сравнение вариантов

| Вариант | Выгода | Основная стоимость |
|---|---|---|
| Bytebase для обеих СУБД | Общая интеграция и существующая логика двух диалектов | Выделение кода, адаптация метаданных, проверка зрелости и скорости |
| Bytebase для Oracle + Postgres Language Server | Специализированный готовый сервер PostgreSQL | Два компонента, разное управление контекстом и настройками |
| ANTLR/c3 для Oracle + готовый провайдер PostgreSQL | Контроль над Oracle-анализатором на TypeScript | Больше собственного семантического анализа |

Рекомендация — сначала проверить первый вариант. Если он не проходит существенные сценарии одной СУБД, сравнить соответствующий отдельный провайдер. Переход к собственной реализации оправдан после установления конкретных пробелов готовых компонентов.

## Контракт интеграции

Вход провайдера: идентификатор и версия документа, диалект, версия сервера, позиция курсора, контекст сессии и версия снимка метаданных. Выход: варианты вставки, их типы и описания, диапазон замены, признак неполноты результата.

Результат применяется только к той версии текста и контекста, для которой был запрошен. Преобразование координат Monaco, протокола и парсера должно учитывать UTF-16, Unicode и UTF-8; одинаковое значение числового смещения в разных компонентах не гарантируется.

Провайдер не владеет транзакцией SQL-вкладки и не запускает редактируемый текст. Для Bytebase предпочтительна передача снимков метаданных из общего кэша. Если выбран сервер с собственным подключением, например Postgres Language Server, его соединение отделяется от пользовательской сессии и согласуется с её схемой, ролью и областью поиска объектов.

Кэш разделяется по СУБД, профилю, базе и эффективному контексту доступа. Смена схемы, роли, search_path или существенных объектов инвалидирует соответствующие данные. Обновление после подключения не должно блокировать редактор; метаданные можно получать постепенно. Нужна явная команда обновления кэша.

Анализ выполняется в изолированном процессе или worker. Новые изменения отменяют устаревшие запросы. Синхронный анализатор должен иметь предел работы или возможность перезапуска worker. Если полноценный провайдер недоступен, редактор сохраняет работу и может предложить ограниченные подсказки ключевых слов и известных объектов без выдумывания контекста.

## Корпус оценки

Техническую проверку кандидатов выполняет ассистент. Основной способ — вызовы провайдера с текстом, позицией курсора и снимками метаданных, проверка ожидаемых подсказок и времени ответа. Для метаданных доступны Oracle 21c XE и разрешённый пользователем [общий тестовый PostgreSQL 10.23](postgres-test-environment.md). Управление окнами PL/SQL Developer для этих проверок не требуется. Пользователь оценивает удобство готовой интеграции на своих запросах. Интерактивный макет содержит подготовленные списки подсказок и не считается испытанием какого-либо движка.

| Сценарий | Что проверяется |
|---|---|
| Таблица после FROM/JOIN | Объекты правильной базы и схемы |
| Колонки после алиаса | Соответствие конкретному источнику; отсутствие колонок соседней таблицы |
| Два одинаковых алиаса во вложенных областях | Правильная область видимости |
| CTE с явными именами и с выводимыми колонками | Имена и состав доступных полей |
| Вложенный SELECT и коррелированный подзапрос | Видимость локальных и внешних источников |
| Незаконченный ввод, комментарии и строки | Устойчивость, отсутствие ложного контекста |
| Quoted identifiers, кириллица и символы вне BMP | Регистр, диапазон замены и координаты |
| Переключение между Oracle и PostgreSQL | Изоляция подсказок и диалекта |
| Смена search_path/схемы и обновление объектов | Корректная актуализация кэша |
| Oracle: пакет, параметры, синоним, %ROWTYPE | Границы расширенной поддержки PL/SQL |
| PostgreSQL: функции и тело PL/pgSQL | Границы процедурной поддержки |
| Быстрый набор большого текста | Отмена устаревшей работы и соблюдение бюджета задержки |

Базовые SQL-сценарии обязательны для MVP. Расширенные процедурные сценарии оцениваются отдельно и используются для определения объёма первой версии. Измеряются также зависимости, размер пакета, запуск, потребление памяти и поведение при недоступной БД.

## Ориентир PL/SQL Developer 17

Изучены локальные главы 23.14 и 25.4 руководства установленного приложения и файл CANames.sql. Code Assistant описывает, среди прочего, члены пакетов, именованные параметры, поля курсоров и записей, %ROWTYPE, последовательности, поля :new/:old и database links. Это функциональный ориентир, а не уже обещанный объём MVP.

CANames.sql настраивает получение имён объектов для контекстных подсказок; он не является самостоятельным движком семантического анализа. В просмотренной поставке и документации плагинов независимый SDK для встраивания Code Assistant в другое приложение не обнаружен. Описание возможностей выше основано на руководстве и файлах поставки; текущий статус практического осмотра приведён в [отдельном документе](plsql-developer-review.md).

## Подтверждение в живом интерфейсе

В отдельном экземпляре PL/SQL Developer 17 с Oracle 21c XE и схемой SQLX проверены вызов F6, колонки по алиасу с типами, фильтрация по префиксу, члены DEMO_PKG, возвращаемый тип функции и вставка именованного параметра с `=>`. [Отчёт и снимки](plsql-developer-review.md).

Эти случаи теперь имеют практический ориентир для сравнения готовых провайдеров. Автоматический вызов при посимвольном наборе, задержка подсказок, сложные области видимости и полнота PL/SQL не измерялись. Проверка возможностей оригинала не означает, что выбранный кандидат автодополнения SQLExplorer уже поддерживает их.
