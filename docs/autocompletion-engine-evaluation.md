# Оценка промышленного движка автодополнения (этап 2 AC-002)

Дата: 2026-09-12. Статус: корпус собран, PostgreSQL-кандидат `omni` прогнан; Oracle-кандидаты и Rust-кандидаты не прогонялись. Решение по движку не принято.

Связанные документы: [архитектура каталога и автодополнения](autocompletion-architecture.md), [исследование кандидатов](autocompletion.md), [единый бэклог](backlog.md).

Этап 2 AC-002 не закрыт. Документ фиксирует метод оценки, исполнимый корпус, базовую линию собственного анализатора и мешающий фактор среды, чтобы оценку можно было выполнить без повторного проектирования.

## Что уже готово к оценке

- Каталог объектов и контекст доступа реализованы ([архитектура](autocompletion-architecture.md), шаги 1–8); кандидатов формирует каталог, поэтому движку для анализа нужны только текст, позиция, диалект и контекст.
- Интерфейс подключения движка — `context-analyzer` в `src/main/context-analyzer.ts`; замена не затрагивает каталог, IPC и UI.
- Корпус исполним: `tests/context-analyzer.test.ts` (12 сценариев) и `tests/completion-service.test.ts` (11 сценариев), включая квалификаторы `sys.`, алиасы до объявления `FROM`, CTE, quoted identifiers, недописанный SQL, лимит и неполноту.
- Проверки на живых БД: `npm run test:db` подтверждает словарные запросы Oracle 21c XE и PostgreSQL 10.23, PUBLIC синонимы, доступность `SYS`, чтение и смену контекста сессии.

## Базовая линия собственного TS-анализатора

| Сценарий корпуса | Состояние | Комментарий |
|---|---|---|
| Таблица после FROM/JOIN | Поддерживается | Квалифицированные и неквалифицированные объекты текущей схемы и `search_path` |
| Колонки после алиаса | Поддерживается | Включая алиас, использованный в SELECT-списке до объявления `FROM` |
| Два одинаковых алиаса во вложенных областях | Частично | Берётся ближайшее объявление; глубина вложенности областей не моделируется |
| CTE с явными и с выводимыми колонками | Поддерживается | Простой select-список верхнего уровня; выражения и `*` не выводятся |
| Вложенный SELECT и коррелированный подзапрос | Не поддерживается | Отдельная работа этапа 2 |
| Незаконченный ввод, комментарии и строки | Поддерживается | Маскирование строк и комментариев, недописанные qualified-имена отбрасываются |
| Quoted identifiers | Поддерживается | Точный регистр и точный префикс; тесты на `"EmployeeData"` |
| Символы вне BMP и координаты | Частично | Текст в UTF-16 JavaScript; отдельного измерения диапазона замены вне BMP нет |
| Переключение Oracle/PostgreSQL | Поддерживается | Изоляция по соединению, документу и контексту |
| Смена схемы/`search_path` | Поддерживается | Селектор схемы, перечитывание контекста после Execute, проверено на живой БД |
| Oracle: пакет, параметры, синоним, `%ROWTYPE` | Вне объёма | AC-003 |
| PostgreSQL: тело PL/pgSQL | Вне объёма | AC-003 |
| Быстрый набор и бюджет задержки | Частично | Устаревшие ответы отбрасываются по последовательности; фактическая задержка — в PERF-001 |

## Кандидаты и их состояние на 2026-09-12

| Кандидат | Язык / процесс | Готовность | Извлечение и стоимость | Лицензия |
|---|---|---|---|---|
| `omni` (Bytebase) | Go, библиотека | PostgreSQL completion проверен на 15 сценариях 2026-09-12; Oracle parser в работе, completion для Oracle планируется | Для PostgreSQL минимально (пакет `omni/pg/completion`, снимок a83efb7); Oracle — ждать или извлекать Bytebase | MIT |
| Bytebase `backend/plugin/parser/plsql` | Go, внутри продукта | Модуль Oracle в ветке main сохранён | Зависит от внутренних структур Bytebase (`base.CompletionContext`, generated protobuf), извлечение требует отдельного слоя | MIT, enterprise-части отделены |
| Postgres Language Server | Rust, готовый LSP | Зрелый: completion, hover, type checking, PL/pgSQL | Собственное подключение к БД и schema cache; Oracle не покрывает | MIT |
| `postgres-lsp` на tree-sitter | Rust/готовый LSP | Заявлен completion и PL/pgSQL | Сведения о правах и работе с живой схемой не подтверждены | требует проверки |
| ANTLR/c3 | TypeScript внутри приложения | Грамматика и движок доступны | Собственная семантика; производительность на PL/SQL под вопросом | BSD/MIT |

## Метод прогона

Для PostgreSQL метод выполнен 2026-09-12 (см. ниже). Шаги для остальных кандидатов:

1. Установить Go (для `omni` и Bytebase) либо Rust (для LSP), собрать обёртку-анализатор с stdin/stdout JSON: `{ text, offset, dialect, currentSchema }` → `{ candidates, elapsedMs }`.
2. Прогнать те же SQL-сценарии корпуса с теми же метаданными и сравнить состав кандидатов и время с базовой линией.
3. При неудаче одного диалекта заменить его отдельным провайдером (для PostgreSQL — LSP), не трогая каталог и UI.
4. Зафиксировать в этом документе: выбранный движок или осознанный отказ, лицензионную границу, размер поставки, изоляцию, отмену устаревших запросов и предел времени анализа.

## Прогон PostgreSQL на `omni` (выполнено 2026-09-12)

Инструмент: `tools/autocompletion-bench` — Go-обёртка над `completion.Complete(sql, offset, cat)` из `omni/pg`, снимок `a83efb7` (2026-09-11). Корпус: 15 сценариев в `corpus.jsonl`, каталог строится из DDL через `catalog.LoadSQL`, `search_path` задаётся `SetSearchPath`. Запуск: установить Go, затем `node tools/autocompletion-bench/run.mjs`.

Результаты:

- Совпадают с базовой линией: объекты по префиксу, колонки по алиасу (включая алиас, объявленный после курсора в SELECT-списке), колонки CTE, колонки после `where alias.prefix`, объекты по `schema.` с префиксом, ключевые слова, колонки по префиксу в `WHERE`.
- Задержка: медиана 0,5 мс, максимум 1,6 мс на 15 сценариях (in-process, без IPC и без загрузки каталога).
- Расхождения:
  1. Пустой префикс после квалификатора (`e.`, `app.`, `recent.`) возвращает только ключевые слова, а не список колонок или объектов.
  2. Quoted identifiers не поддерживаются: `"Emp` не извлекается как префикс (`extractPrefix` понимает только `[A-Za-z0-9_]`), кандидатов нет.
  3. Квалификатор схемы не изолирован: `from app.emp` вернул `public."EmployeeData"` из `search_path`, а также неясный кандидат `EMPTY`.
  4. Кандидат `emp` без квалификатора имеет неясный источник (вероятно, расширение или тип); требует изучения при интеграции.
- Вывод для PostgreSQL: движок быстрый и контекстный, но три расхождения должны компенсироваться нашей стороной (перечисление при пустом префиксе, quoted identifiers, изоляция схемы). В текущем виде как полная замена TS-анализатора не проходит корпус; как анализатор при непустом префиксе перспективен.

## Oracle

`omni` Oracle completion не готов, Bytebase `plsql` требует извлечения из внутренних структур Bytebase (`base.CompletionContext`, generated protobuf). Прогон не выполнялся.

## Rust-кандидаты

`cargo` и `rustc` в среде отсутствуют; Postgres Language Server и `postgres-lsp` не прогонялись. При появлении Rust toolchain метод тот же: LSP/CLI-вызов с текстом, позицией и снимком схемы.

## Решение на 2026-09-12

Оставляем собственный `context-analyzer` как рабочий анализатор. Для PostgreSQL `omni` подтвердил скорость и контекст, но требует закрытия трёх расхождений, поэтому интеграция возможна как дополнительный источник кандидатов, а не как замена. AC-002 остаётся открытым: нет результата по Oracle и нет решения по интеграции PostgreSQL-кандидата.
