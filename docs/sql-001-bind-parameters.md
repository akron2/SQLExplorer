# Bind-параметры и интерфейс задания значений: архитектура

Дата: 2026-09-17. Статус: реализовано и проверено 2026-09-17. Задача: [SQL-001](backlog.md).
Связанные документы: [архитектура](architecture.md), [бэклог](backlog.md), [поддержка LOB](lob-support-architecture.md).

## Цель и критерии успеха

1. Перед запуском SQL с параметрами приложение извлекает bind-параметры из выполняемого выражения и показывает диалог задания значений.
2. Поддержаны типы String, Number, Date и NULL; пустая строка — валидное значение, NULL — явный флажок.
3. Именованные `:name` работают в Oracle и PostgreSQL одинаково; в PostgreSQL дополнительно работают нативные `$1..$n`, включая смешение обоих синтаксисов в одном выражении.
4. Значения параметров не сохраняются: живут только в памяти вкладки, не попадают в рабочую область, историю, логи и файлы.
5. Выполнение, повторный запуск, отмена и сообщения об ошибках покрыты интеграционными тестами на живых Oracle и PostgreSQL.

## Ограничения и допущения

- Единица выполнения — выражение у курсора или выделение (как для обычного запуска): параметры извлекаются из фактически выполняемого текста, а не из всего документа.
- Только направление IN. `INTO :x`/`RETURNING INTO` в PL/SQL и OUT/IN OUT остаются за PROC-001; сервер вернёт свою ошибку — она не маскируется.
- Oracle позиционные `:1` не поддерживаются и дают явную ошибку клиента, а не молчаливый пропуск. Oracle `&var`-подстановки SQL*Plus вне объёма.
- Типы Boolean, RAW/BYTEA (hex-ввод) и параметры-массивы вне MVP.
- Значения — только примитивы: строка, число, дата, NULL. Значение не ограничивается в размере, кроме общих лимитов запроса.
- Нумерация `$n` в PostgreSQL для пользователя вторична: номера присваиваются по порядку первого вхождения и могут переехать при добавлении именованных параметров перед ними.

## Выбранное решение

### Поток выполнения

```
Execute (F5/F9) → getSqlToExecute() → extractParameters(sql, dialect)   [shared]
  ├─ параметров нет → запуск как раньше
  ├─ ошибка извлечения (напр. Oracle :1) → сообщение в панели результата, без IPC
  └─ параметры есть → диалог (предзаполнен памятью вкладки)
        ├─ Отмена → запуска нет
        └─ Выполнить → api.execute({ sql, parameters })
              worker: повторная экстракция + валидация + конвертация
              ├─ Oracle: named binds {NAME: value}
              └─ PostgreSQL: переписывание :name/$n → $k + массив значений
```

Worker не доверяет renderer: он повторно извлекает параметры той же общей функцией и сверяет их с присланными значениями. Лишние или недостающие значения дают ошибку `kind: 'bind'`.

### Правила экстракции (один сканер в shared)

| Контекст | Oracle | PostgreSQL |
|---|---|---|
| Синтаксис | `:name`, имя `[A-Za-z_][A-Za-z0-9_$#]*` | `:name` (тот же вид) + нативные `$1..$n` |
| Внутри `'…'`, `"…"`, `--`, `/* */` | пропуск | пропуск |
| Dollar-quote `$tag$…$tag$` | — | пропуск |
| q-строки `q'[…]'` (4 вида скобок и произвольный символ-разделитель; только диалект Oracle) | пропуск | — |
| `::` каст | — | пропуск, не параметр |
| `:=` присваивание | пропуск сам оператор; `x := :v` → `:v` параметр | так же |
| Регистр имён | без учёта: `:X` ≡ `:x`, канонический ключ и отображение — в верхнем регистре | с учётом регистра, отображение — как в первом вхождении |
| Повтор имени | одна строка диалога, один named bind на все вхождения | одно `$k` на все вхождения |
| Oracle `:n` (позиционные) | явная ошибка «не поддерживаются» | — |

Вложенные блочные комментарии PostgreSQL (`/* /* */ */`) не поддерживаются сканером — как в существующем сплиттере выражений; задокументированное ограничение.

### PostgreSQL: смешение `:name` и `$n`

Единая позиционная нумерация по порядку первого вхождения: все параметры (именованные и нативные) образуют один список в порядке появления в тексте, каждому присваивается `$1..$K`, и SQL переписывается соответственно.

Пример: `where a = :x and b = $1 and c = :x` → порядок `x`, `$1` → SQL `where a = $1 and b = $2 and c = $1`, значения `[v(x), v($1)]`, в диалоге две строки: `x` и `$1`.

Массив значений не содержит дыр, поэтому сервер не выдаёт ошибки вида «bind message supplies N parameters…».

### Контракты

```ts
type BindValueType = 'string' | 'number' | 'date' | 'null';
interface BindValue { type: BindValueType; value: string; }   // при null значение игнорируется

interface ExecuteRequest {
  // было: parameters?: Record<string, boolean | number | string | null>
  parameters?: Record<string, BindValue>;   // ключ: каноническое имя или "$n"
}
// DatabaseErrorKind пополняется вариантом 'bind'
```

Конвертация в worker: `string` — как есть; `number` — строгий парсинг (NaN/±Infinity → ошибка `bind`); `date` — ISO `YYYY-MM-DD[ T]HH:MM[:SS[.fff]]`, для Oracle превращается в `Date` локального времени, для PostgreSQL уходит строкой (сервер кастует по контексту); `null` — `null`.

### Диалог

- Строки в порядке первого вхождения; повторное имя — одна строка. Колонки: имя (readonly), тип (String/Number/Date), значение, флажок NULL (поле значения гаснет).
- Предзаполнение из памяти вкладки (`documentId → Record<name, BindValue>`); новый параметр — String, пустое значение. Пустая строка — валидное значение.
- Ошибки формата числа/даты подсвечиваются inline и блокируют выполнение. Enter — выполнить, Esc — отмена.
- SQL в диалоге не показывается: список параметров достаточен, SQL виден в редакторе.
- Память значений: `useRef` по `documentId` в renderer; очищается при закрытии вкладки; не участвует в сохранении рабочей области.

### Сообщения об ошибках

- Недостающее значение / лишний ключ / неверный формат числа или даты → `kind: 'bind'`, текст без значений параметров; в панели результата заголовок «Ошибка параметра».
- Ошибки сервера (ORA-01008, ошибки типов PostgreSQL) проходят как `kind: 'sql'` с серверным текстом.

## Ключевые решения и их обоснование

| Решение | Альтернативы | Почему так |
|---|---|---|
| Модальный диалог перед запуском, предзаполнен памятью вкладки | Постоянная панель параметров; молчаливый повтор последних значений | Как в PL/SQL Developer: предсказуемо, минимум UI-рисков; молчаливый повтор создаёт риск незаметного запуска с устаревшими значениями |
| Единая экстракция в shared, worker перепроверяет | Парсер только в renderer | Один источник правил; worker не доверяет renderer — рассинхрон диалога и запроса невозможен |
| `:name` едины для обеих СУБД, PG дополнительно `$n`, общая позиционная нумерация | Только `:name`; `$n` без перенумерации | Привычно пользователям pg; перенумерация по порядку вхождения даёт единственную простую семантику и массив без дыр |
| Типы String/Number/Date/NULL с конвертацией в worker | Всё строками; типизация в renderer | Строки на Oracle рискуют NLS/неявными конверсиями; worker — владелец типов и валидации |
| Пустая строка валидна, NULL — флажок | Пустое = NULL | Нельзя случайно отправить NULL в NOT NULL колонку |
| Значения только в памяти вкладки | Сохранение «удобных» значений | Чувствительные данные не должны покидать память без явного решения пользователя |
| IN только | Полная поддержка OUT | OUT/IN OUT тянет REF CURSOR и DBMS_OUTPUT — территория PROC-001 |

## Отклонённые альтернативы

- **Постоянная панель параметров вкладки (DBeaver)**: удобнее для итераций, но заметно больше работы и постоянное место на экране; диалог покрывает сценарии MVP.
- **Диалог только при изменении набора параметров**: экономит клик, но молча переиспользует прошлые значения — риск для корректности.
- **`$n` PostgreSQL без поддержки `:name`**: ломает единый UX двух СУБД и привычку пользователей Oracle.
- **Поддержка Oracle позиционных `:1`**: редкий сценарий, конфликтует с моделью именованных binds; явная ошибка честнее молчаливой поддержки.
- **Boolean и hex-ввод BYTEA/RAW**: спорные конвенции ввода без подтверждённых сценариев; отложено.

## Риски и открытые вопросы

По итогам реализации:

- Повторение одного именованного bind в Oracle подтверждено живым тестом: один named bind обслуживает все вхождения (`:v || :v` → `abab`).
- Даты Oracle: `Date` локального времени подтверждён `to_char`-проверкой с точностью до минуты; формат вывода DATE в выборке остаётся под сессионным NLS (`DD-MON-RR` по умолчанию) — это поведение сервера, не клиента.
- Даты PostgreSQL: строка кастуется сервером по контексту; в выборке `date` приходит как ISO-строка в локальном часовом поясе драйвера — тесты сравнивают через `to_char`, чтобы не зависеть от TZ.
- PostgreSQL бестиповые позиции (`SELECT $1`) дают серверную ошибку «could not determine data type» — это честное серверное сообщение, не ошибка клиента.
- Сканер не понимает вложенные блочные комментарии PostgreSQL — ограничение, общее с существующим сплиттером выражений.

## План реализации

Выполнен:

1. Shared: модуль `sql-binds.ts` — сканер-экстрактор (`extractSqlParameters`, `uniqueSqlParameters`, `rewritePostgresSql`), конвертация значений (`parseBindValue`).
2. Контракты: `BindValue`, `BindValueType`, `DatabaseErrorKind += 'bind'`, новый тип `parameters` в `ExecuteRequest`.
3. Worker: валидация и конвертация для Oracle (named binds) и PostgreSQL (переписывание + массив), ошибки `kind: 'bind'`; bind-ошибка PostgreSQL не помечает транзакцию изменённой.
4. Renderer: `BindParametersDialog`, вызов из `execute()` в App.tsx, память значений по вкладке (очищается при закрытии), обработка `kind: 'bind'`.
5. Mock-api: приём параметров для browser-сценариев.
6. Тесты: 19 юнит-тестов экстрактора и конвертации; живые сценарии `npm run test:db` (string/number/date/null, повтор имён, регистр, смешение `$n`/`:name`, повторный запуск, недостающие и неверные значения); Electron E2E диалога (открытие, отмена, предзаполнение, inline-валидация, повторный запуск, `$n`+`:name` на живом PostgreSQL).
7. Документы: бэклог, README, статус реализации.
