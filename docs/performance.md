# Отзывчивость SQLExplorer и план измерений

Дата: 2026-09-09. Статус: проектные цели; фактических результатов пока нет.

Связанные документы: [архитектура](architecture.md), [автодополнение](autocompletion.md).

## Основной сценарий

Пользователь сообщает о зависании PL/SQL Developer при разворачивании главного окна с множеством внутренних рабочих окон. По его предположению, приложение начинает перерисовывать их все. RDP — контекст наблюдения; отдельная неисправность RDP не установлена и не является предметом архитектуры SQLExplorer.

Требование: восстановление окна с одинаковым видимым содержимым должно оставаться быстрым при увеличении числа скрытых документов.

## Правила реализации

- Текстовая модель документа существует независимо от его отображения.
- На одну видимую область приходится один редактор Monaco и только необходимые видимые панели результата.
- У скрытых документов нет смонтированных редакторов и таблиц, участвующих в layout или render.
- Переключение вкладки восстанавливает её состояние без пересоздания моделей остальных документов.
- События изменения размера и восстановления окна не вызывают обход всех скрытых представлений.
- Обновление данных одной вкладки не запускает пересчёт содержимого всех вкладок.
- Запросы к БД, анализ SQL, экспорт и тяжёлое преобразование значений выполняются вне потока интерфейса.
- Порции данных и объём очереди IPC ограничены; получатель определяет темп дальнейшего чтения.

Документы всё равно занимают память, а заголовки вкладок требуют обработки. Требование касается устранения работы тяжёлых скрытых представлений; абсолютная независимость всех затрат от количества документов не заявляется.

## Начальные ориентиры

Показатели ниже предложены для первого цикла измерений. Они не являются результатами тестов или гарантией для неизвестного оборудования.

| Показатель | Цель / правило |
|---|---|
| Запуск до возможности редактировать | Ориентир до 2 секунд на согласованной машине; сеть не входит в обязательный путь запуска |
| Переключение среди 50 прогретых документов | P95 до 100 мс |
| Подсказки из прогретого кэша | P95 до 150 мс от действия пользователя до появления списка, включая задержку запуска |
| Восстановление с 1 и 100 документами | Начальный ориентир: разница P95 не более 50 мс при одинаковом видимом содержимом |
| Первое получение результата | Порция 200–500 строк; отдельно измеряются сервер, передача и отображение |
| Кэш строк результатов | Предварительно 128 MiB суммарно; это бюджет данных приложения, а не всей памяти процессов |
| Повторное сворачивание/восстановление | После стабилизации не растут число редакторов, подписок и используемая память из-за самих циклов |

В бюджет памяти нужно включать расходы представления данных и буферов, а не только длину строк. Драйвер, IPC, движок редактора и Chromium также расходуют память и измеряются отдельно. Значение 128 MiB уточняется по реальной нагрузке.

## Протокол восстановления окна

Распределение проверки согласовано с пользователем: практическую оценку удобства и зависаний на своей машине проводит пользователь; ассистент готовит технические измерения и анализирует причины задержек. Проверка на практике дополняет инструментальный протокол. Неисправности автоматизации сторонних окон не являются основанием считать производительность SQLExplorer проверенной или отказаться от замеров внутри будущего приложения.

1. Зафиксировать версии ОС, приложения, Electron, CPU, объём памяти, разрешение, масштаб, число мониторов и режим подключения к рабочему столу.
2. Подготовить варианты с 1, 20 и 100 открытыми документами. Для первичного синтетического профиля скрытые документы могут иметь по 64 KiB текста. Активный документ, размер окна и отображаемый результат одинаковы во всех вариантах.
3. Дождаться загрузки моделей и стабилизации фоновых операций. Холодное открытие документов измерять отдельно.
4. Выполнить не менее 30 циклов сворачивания и восстановления для каждого варианта; порядок вариантов чередовать, чтобы прогрев не давал систематического преимущества.
5. Измерять время от обработки события восстановления до кадра с рабочей областью и готовности обработать ввод. Отдельно фиксировать затраты main и renderer, долгие задачи, layout/render и CPU.
6. Сохранить распределения, медиану, P95, память процессов и число живых редакторов. Визуально проверить отсутствие мигания, пустых областей и потери фокуса.
7. Повторить сценарий с двумя видимыми областями и с активной таблицей результатов.

Время передачи кадра по RDP не смешивается с локальным временем обработки приложения. После локальной проверки сценарий воспроизводится в рабочем окружении пользователя. Дополнительно проверяются изменение размеров и масштаба, поскольку они также вызывают перерасчёт видимой области.

Признак архитектурной ошибки: при восстановлении создаются новые редакторы для скрытых вкладок, запускается пересчёт их таблиц или основной вклад в задержку растёт вместе с их числом.

## Другие обязательные сценарии

| Сценарий | Ожидаемое поведение |
|---|---|
| Подключение к недоступной БД | Редактор и другие вкладки доступны; таймаут не блокирует UI |
| Длинный запрос Oracle и запрос PostgreSQL одновременно | Независимое выполнение в пределах лимитов сессий |
| Большая выборка с широкими строками | Постепенная загрузка, ограниченная память и понятный признак неполноты |
| Большой CLOB/BLOB, JSON или бинарное значение | Просмотр по запросу; полное значение не загружается для каждой ячейки автоматически |
| Прокрутка широкой таблицы | Создаются только необходимые строки и колонки |
| Экспорт большого результата | Ограниченные буферы, прогресс, возможность остановки, отзывчивый редактор |
| Отмена выполнения и остановка получения строк | Видимое состояние запроса отмены и корректное освобождение соответствующего ресурса |
| Быстрый набор и удаление SQL | Устаревшие подсказки не появляются после изменения текста |
| Обновление большой схемы | Фоновая загрузка с приоритетом нужных объектов |
| Многократное открытие и закрытие вкладок | Освобождаются редакторы, модели закрытых документов, курсоры и подписки |
| Обрыв соединения или сбой DB-worker | Документы сохраняются, исход выполнения обозначен честно, автоматического повтора SQL нет |

Для числовых и временных типов проверяется не только скорость: значения должны сохранять точность и смысл после получения, отображения, копирования и экспорта.

## Политика результатов для MVP

Первый вариант реализации хранит полученные порции в ограниченном кэше. При достижении бюджета дальнейшая подгрузка останавливается; приложение показывает причину и предоставляет возможность потокового экспорта или освобождения результатов.

Экспорт должен учитывать уже полученные строки и оставшийся курсор. Нельзя незаметно повторять запрос, чтобы получить начало результата: база могла измениться. Если для конкретной операции нужен новый запуск, он оформляется отдельно.

Автоматическая подкачка произвольного количества строк на диск не входит в исходный MVP. Её необходимость оценивается после уточнения рабочих объёмов. Виртуализация grid сама по себе не ограничивает память загруженных данных.

## Отчётность и изменения целей

Для каждого измерения сохраняются окружение, версия сборки, параметры корпуса и результаты. Фактические показатели добавляются отдельным отчётом после появления приложения; этот документ пока не содержит выполненных тестов.

Если цель не достигнута, сначала определяется источник задержки: восстановление представлений, подписки, анализ текста, передача данных, работа драйвера или отрисовка. Изменение фреймворка рассматривается после такого измерения. Корректировка бюджетов должна сопровождаться причиной и обновлением документа.

## Первые наблюдения референса

В PL/SQL Developer 17 выполнена одна проверка сворачивания и восстановления с двумя SQL-документами: текущий текст и результат сохранились. Во время DBMS_SESSION.SLEEP во втором окне удалось переключиться к первому результату. Проверки на 20/100 документов и непрерывного измерения задержек пока нет.

При открытии Preferences в исходном экземпляре получен кадр со статусом «Не отвечает», затем настройки открылись. Это отдельное наблюдение при инструментальном осмотре, а не воспроизведение массовой перерисовки при восстановлении. Причина и вклад инструмента не установлены. [Подробный отчёт](plsql-developer-review.md).

Показанные в интерфейсе времена SELECT и попытки отмены на DBMS_SESSION.SLEEP не используются как сравнительный бенчмарк. Проектные цели SQLExplorer выше остаются непроверенными до реализации приложения.
